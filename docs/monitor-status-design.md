# 状态面板设计：三层指标观（快诊 + AI 深体检）

> 2026-10-04 定稿。演化链：四指标卡 → 简易表格 → 表格折叠进详情 → **纯 AI 诊断（最终形态）**。
> 本文是产品逻辑的单一真源；实现见 `ui/server.py`（采集/解析/诊断）与 `ui/static/index.html`（渲染）。

## 一、核心命题

传统监控面板回答的是「**设备健康吗**」——CPU、内存、错包，这是设备视角的体温计。
但中小企业排障时用户真正问的是三个问题：

1. **网通不通、慢在哪？**（体验）
2. **设备还撑得住吗？**（资源）
3. **谁动过什么？**（变化）

状态面板按这三层组织指标，**状态徽章由体验型指标优先决定**——设备体温正常 ≠ 用户没断网。

## 二、三层指标清单

### 体验型（决定徽章语义）

| 采集点 | 命令（华为 / 思科） | 抓什么故障 | 判色 |
|---|---|---|---|
| 出口连通 | `ping 223.5.5.5` | 出口断/慢 | 丢包>0 warn，≥20% bad |
| DNS 解析 | `nslookup www.baidu.com` | 解析故障 | 失败=bad |
| NAT 会话水位 | `display nat session statistics` / `show ip nat statistics` | 会话耗尽=全网断 | ≥80% warn，≥90% bad |
| DHCP 池余量 | `display ip pool` / `show ip dhcp binding` | 池耗尽=新终端进不来 | ≥90% warn，≥95% bad |

### 资源型（设备体温）

| 采集点 | 说明 |
|---|---|
| CPU / 内存 / 错包增量 | 已有；错包只看「相对上次新增」，计数器回绕自动弃用 |
| 接口占用率 / 接口 up 对比 | 已有 |
| **光模块收光功率** | `display transceiver diagnosis`；**比 CRC 早几周的预警**（CRC 出现时链路已坏，光衰是"将坏未坏"）。<-20dBm 过弱 / >-3dBm 过强 |
| 温度/电源/风扇 | 深体检覆盖 |

### 变化型（netdev 独有优势：有基线，能报"什么变了"）

| 采集点 | 说明 |
|---|---|
| **配置漂移** | 每次快诊对 `display current-configuration` 取 SHA-256，与上次基线对比。报警内容：「上次采集后配置被人改过」——比任何指标都值钱 |
| **ARP 表项突增** | 环路/病毒扫描的前兆，比环路日志更早。+50 条或翻倍 warn |
| 接口翻动 / STP/拓扑 / 路由邻居 / 环路 | logbuffer 自动分类（5 类线索） |

## 三、两个触发档位

| | ⟳ 快诊 | 🔍 深体检 |
|---|---|---|
| 定位 | 日常 | 「说不上哪不对就是不对」 |
| 内容 | 固定指标（13 行事实清单） | **AI 规划 5~20 条只读命令**全跑一遍 |
| 时长 | 秒级 | 1~3 分钟 |
| AI 角色 | 解读结构化数据 | **规划采集 + 解读全部回显** |

## 四、AI 纪律（不可破）

1. **AI 不接管实时链路**：采集/解析/判色由代码负责（可重复、离线、零成本），AI 只在人工触发时做解读；喂给 AI 的是**结构化事实**（rows/delta/log），明令禁止编造没给的数值。
2. **只读闸门双重过滤**：深体检命令必须过两道门——`display/show` 前缀白名单 + 写操作黑名单（undo/save/reset/reboot/clear/…）；逐条再过 `netdev run` 自身的四道闸门。被拦命令不执行但**如实展示**（"另有 N 条被只读闸门拦下"）。
3. **降级不瞎**：设备不支持某指标 → 该行 "--"（绝不当 0）；AI 未配置/解析失败 → 黄条说明原因。
4. **人工触发**：两个档位都只在用户点按钮时跑，没有后台轮询、不打扰、不烧额度。

## 五、多厂商机制

命令差异大（NAT/DHCP/光衰各家不同），沿用既有机制，不新造轮子：
平台档案首选命令（`lib/platforms.py` PROFILES）→ 候选探测（CANDIDATES）→ AI 学规则缓存（cache_put，学了就一直用）→ 不支持静默降级。

已知边界：光衰解析目前支持华为/华三冒号格式（`Rx Power(dBm): -12.50`），思科表格式暂降级 "--"。

## 六、UI 约定

- 主视图 = 徽章（正常/留意/异常，语义色 `--st-on/--warn/--bad`）+ 一句话总结 + 逐条「情况 → 建议」，条与条之间**虚线横线分割**。
- AI 输出约束：快诊 ≤4 条、深体检 ≤6 条；title ≤12 字短语；detail 引用具体数值；action 只给一条命令。
- 深体检计划可折叠查看（`<details class="dplan">`），执行明细可审计。
- 指标数值表格已按用户决策移除——面板只呈现结论；原始数据在服务端日志与基线 JSONL（`live/monitor/<设备>.jsonl`）里可追溯。

## 七、同屏通道工程实录（2026-10-04 真机 AR111-S 四轮实测）

串口被前台窗格占用时采集走同屏（物理独占绕不开），这一路没有逐条回显、只有一整块屏幕，
四轮真机踩出四条硬教训，全部有回归守门（`tests/test_monitor.py` 组[7]）：

1. **同屏必须等提示符回来再发下一条**（`_wait_prompt`）。固定 sleep 是在赌时间：
   ping 4 包全超时要 ~9s（每包 2s），等短了统计行没出来；更糟的是前一条没跑完就敲
   下一条时，VRP **执行期间不回显输入**，下一条的回显整个消失。
   实现：末行从「裸提示符」变成回显/输出 = 已开始；末行变回裸提示符 = 跑完（上限 ~19s）。
2. **切段必须倒序 rfind 锚定最新一轮**（`_split_screen_by_cmds`）。tmux 滚动缓冲跨轮次
   保留，900 行屏里常有上一轮的回显残留；正序 find 会锚到上一轮，切出「上一轮 ping →
   本轮 nslookup」的跨轮巨段，混进旧 Error 文本后被 `_bad_echo` 整段否决——ping 明明
   采到了却显示「未采集」。段尾兜底用「下一个裸提示符行」，不用屏幕末尾。
3. **ping 全超时必须报丢包，不能装「未采集」**。统计行没出来/没有时，用
   「Request time out 包数 + time= 成功包数」估丢包——出口真不通是事实，
   吞掉它等于把最重要的故障藏起来（实测：AI 正确判「出口连通中断 → 检查上联链路」）。
4. **华为 `display ip pool` 每池把数字印两遍**（Pool-name 明细块 + IP address Statistic
   汇总块），直接求和双倍记账；有 "Pool-name" 时按池分段、每段取最后一个 Used/Idle。
   另：同屏轮次的 900 行屏截不出完整配置，**配置漂移哈希只认直连全量回显**，
   同屏轮次不参与，否则同一份配置会反复误报「已变更」。
